# Data and paths

Where Aria keeps its files, sockets, services and keys, on Omarchy, on macOS and on a hub, which of them are secret and
which are safe to delete. It is for you when you back up, clean up, debug or uninstall.

Stop Aria before you delete anything under the data folder (`aria quit`, or `systemctl --user stop aria.service` on
Omarchy, `systemctl --user stop aria-serve.service` on a hub). A running service rewrites its files and may recreate
what you removed.

## The three setups at a glance

| | Omarchy (Linux desktop) | macOS | Hub (headless Linux) |
|---|---|---|---|
| Data folder | `~/.aria` | `~/.aria` | `~/.aria` on the server |
| Runtime folder (sockets, face file) | `$XDG_RUNTIME_DIR/aria` | `~/.aria/run` | `$XDG_RUNTIME_DIR/aria` |
| Live credential copies | `$XDG_RUNTIME_DIR/aria-secrets-<id>` | `aria-secrets-<id>` in the per-user temporary folder | none: the keyring is off, the files are plain |
| Service | systemd user unit `aria.service` (`aria dock`) | LaunchAgent `com.aria.dock` (`aria dock`) | systemd user unit `aria-serve.service` (`aria serve`) |
| Keyring | Secret Service, through `secret-tool` | login keychain, through `security` | off (the settings `aria hub init` sends have `credentials.keyring` set to `false`) |
| Output of the service | the user journal (`journalctl --user -u aria.service`) | `~/.aria/logs/aria.log` | the user journal (`journalctl --user -u aria-serve.service`) |
| Aria's face | widget in the Omarchy bar | in the dock's notch wing | none |

`ARIA_HOME` moves the data folder: set it and every `~/.aria` below is `$ARIA_HOME` instead. On macOS the runtime folder
follows it (`$ARIA_HOME/run`). On Linux the runtime folder does not: it stays in `$XDG_RUNTIME_DIR/aria` whatever
`ARIA_HOME` is, so two instances with different homes share one control socket. The live credential folder and the keyring
service name do follow the home (see [the keyring](#the-keyring)).

## The data folder

Everything Aria stores for you is in `~/.aria`, mode `700`. The repository never holds user data.

### Files

| Path | What | Secret? | Safe to delete? |
|---|---|---|---|
| `settings.json` | Every setting ([settings](../settings.md)). Keys Aria does not know are kept when it saves. | No | Yes, but you lose your choices and the setup runs again |
| `sessions.json` | The open tabs: id, title, the chain of Pi session ids, the folder, which tab is active. A copy that cannot be parsed is moved to `sessions.json.broken`. | Private: tab titles and folders | Yes, but the tabs close; the conversations stay in `agent/sessions/aria/`, and at the next start the checkpoints and notices of every session that is not open are removed |
| `schedules.json` | The scheduled tasks: prompt, time, days or date, permissions, last run and result ([automation](../guide/automation.md)). A broken copy is moved to `schedules.json.broken`. | Private: it holds your prompts | No: you lose the tasks |
| `jobs.json` | The background jobs the service ran: how each ended, a subagent's result, and the last 20 lines of output of an end note not yet delivered. | Private: output can hold anything | Yes, with Aria stopped; undelivered end notes are lost |
| `secrets.json` | The names of the secrets you keep, what each is for and when it was saved. Never a value. | Names only | No: the values would stay in the keyring with no name in Aria |
| `mcp.json` | The MCP servers (Notion, Tavily, Engram, the ones you import or install), in Pi's format. With the keyring on, the headers of a remote server and the `env` values with a secret-looking name are `!aria secret …` commands; with it off, the values themselves. An argument or another value you wrote there stays as written. | Only with the keyring off, and a value you put in `args` is always in the file | No: you lose the connectors (their keys stay in the keyring) |
| `auth.json` | Your provider sign-ins, in Pi's format. With the keyring on it is not in this folder: it is sealed in the keyring and a live copy sits in the runtime location of the table above while the service runs. With it off, a plain file here. | Yes | Yes: you sign in again |
| `mcp-auth.json` | The MCP sign-in state (registered client, tokens), in Pi's format. Same placement as `auth.json`. | Yes | Yes: you sign in to the connectors again |
| `hubs.json` | On the computer you connect from: the hubs `aria hub init` linked, as `{"default": "ana@srv", "hubs": {"ana@srv": {"key": "/home/ana/.ssh/aria-hub"}}}` (mode `600`). `aria connect` with no host opens the default one, and a host listed here is reached with its own key. It holds no secret: the key is a path. | Yes | Yes: run `aria hub init` again |

### Folders

| Path | What | Secret? | Safe to delete? |
|---|---|---|---|
| `agent/` | Pi's directory, regenerated by Aria. What is inside, and what you can edit, is [below](#the-agent-folder). | Conversations are private | Not as a whole: it holds the conversations and the packages the installer put there |
| `pi/<version>/` | The pinned Pi engine, one folder per version (the version is in the repo's `pi-version` file). | No | Old versions, yes. The current one only if you run the installer again |
| `bin/` | First on the `PATH` of every Pi process: `pi` (a shim Aria rewrites to the pinned version), and links the installer makes: `node`, `claude` (when Claude Code is installed), `engram`, `agent-browser`. | No | Not by hand: run the installer again to rebuild it |
| `engram/` | Aria's own memory database (Engram), apart from any Engram you have. | Private | No: this is Aria's memory |
| `attachments/` | Files you attached to messages: `<session>/<yyyy-mm-dd>/<n>-<safe name>`. Folders `700`, files `600`. Aria never removes them. | Private | Yes, but messages that mention a file lose it |
| `checkpoints/` | One git repository per session, `checkpoints/<session>/`, that keeps the session's folder as it was before each message, for undo. The project's own `.git` is not touched. | Private: it holds copies of your files | Yes: undo history goes. Aria removes a session's folder when you close its tab |
| `notices/` | `<session>.jsonl`: the notices a tab was shown (at most 500 kept). | Private: a notice can name your files | Yes. Removed with the tab |
| `models/` | The dictation model, downloaded the first time you dictate. A `.part` file is a download in progress. | No | Yes: the next dictation offers to download it again |
| `node/` | A hub whose Node was missing or older than the minimum: the pinned Node (`node-version`), apart from the system's. | No | No, while the hub runs on it |
| `agent-browser/<version>/` | The pinned `agent-browser` (`agent-browser-version`) the agents use to check pages. Optional on a hub. | No | Yes: the browser check stops working |
| `logs/` | macOS: `aria.log`, the LaunchAgent's output. | May show your messages and paths | Yes |
| `run/` | macOS only: the runtime folder ([below](#sockets-and-runtime-files)). | No | Not while Aria runs |
| `hub-src/` | On a hub: what `aria hub init` uploaded (installer, unit, version pins, the binary). | No | Yes, once init finished; the next init uploads it again |

### Leftovers and backups

| Path | What | Secret? | Safe to delete? |
|---|---|---|---|
| `<name>.bak` | On a hub, `settings.json`, `auth.json`, `mcp.json` and `mcp-auth.json` as the hub had them before `aria hub init --settings` or `--credentials` replaced them the first time. Never overwritten by a later import. | `auth.json.bak`, `mcp.json.bak` and `mcp-auth.json.bak`: yes | Yes, when you do not need the old copy |
| `sessions.json.broken`, `schedules.json.broken` | The unreadable file, kept when Aria started over. | Like the original | Yes, after you looked |
| `.<name>.<pid>.<n>.tmp` | A temporary file of an atomic write. Only a crash leaves one. | Like the original | Yes |

## The agent folder

`~/.aria/agent/` is Pi's directory (`PI_CODING_AGENT_DIR`). Aria rewrites parts of it at every session start from your
settings. Aria remembers what it wrote, with a hash, in `.aria-files`. A file you edited, or a hash that no longer
matches, is yours: Aria keeps it, does not apply its own updates to it, and says so in the chat. A file you deleted stays
deleted. To get Aria's version back, delete the file and its line in `.aria-files`.

| Path | What | Yours to edit? | Safe to delete? |
|---|---|---|---|
| `SYSTEM.md` | The persona, rendered from `assistant.*`, `git.*`, `memory.*` and `subagents.*`. | Yes: your version is kept | Not alone: a file you delete stays deleted while `.aria-files` lists it. Delete its line too and it is rewritten |
| `agents/<expert>.md` | The experts (`frontend`, `backend`, `security`, `reviewer`, `researcher`). A disabled expert's file is removed. | Yes: your version is kept | Not alone: a deleted file stays deleted while `.aria-files` lists it |
| `extensions/` | Aria's Pi extensions (router, sandbox, quota fallback, connectors and the rest). | Yes: your version is kept | No: a deleted extension stays deleted while `.aria-files` lists it, and the sandbox and the connector gate are extensions |
| `skills/` | Aria's own skills (`install-from-link`, `slice`, `verify-in-browser`) and the skills you ask Aria to install. | Yes | Your installed skills would be lost, and a deleted skill of Aria's stays deleted while `.aria-files` lists it |
| `settings.json` | Pi's own settings: the package list, the default model, the compaction reserves. Aria merges its keys into it and keeps the others. | Yes, for keys Aria does not set | No: it lists the installed packages |
| `aria.json` | What the extensions read from your settings (models, quota, effort, compaction, router, the conversation language, sandbox, subagents, connectors). No secrets. | No: regenerated at every session start, and locked against the model | Yes: rewritten |
| `auth.json`, `mcp.json`, `mcp-auth.json` | Links to the credential files above. A real file you put here is left alone. | No | Yes: relinked |
| `npm/`, `git/` | The pinned packages (`pi-packages`) the installer installed with Pi. | No | No: run the installer again to bring them back |
| `sessions/aria/` | Every conversation, one `<timestamp>_<session id>.jsonl` per segment. | No | No: these are your conversations |
| `sessions/subagents/` | A subagent's session, when `subagents.saveSessions` is on. | No | Yes |
| `.aria-files`, `.compaction-percent` | Aria's record of the files it wrote, and the compaction share it last applied. | No | Not by hand |

Pi writes other files of its own here (`models-store.json` is one). They are Pi's.

The model cannot change `extensions/`, `agents/`, `SYSTEM.md`, `settings.json`, `aria.json` or `.aria-files` with its write
and edit tools or from a sandboxed command, whatever a session granted, and neither `~/.aria/settings.json` nor
`attachments/`: a model that could edit them could switch the sandbox off ([safety](../guide/safety.md)).

## Sockets and runtime files

The service keeps these in the runtime folder: `$XDG_RUNTIME_DIR/aria` on Linux, `~/.aria/run` on macOS. On Linux, when
`$XDG_RUNTIME_DIR` is empty or unset, Aria uses `/run/user/<uid>/aria` if `/run/user/<uid>` exists (a non-login ssh may not
set the variable), and `/tmp/aria` otherwise. The folder is created `700`. On Linux it is normally in memory, so nothing
in it survives a reboot; all of it is rebuilt at the next start.

| Path | What | Secret? | Safe to delete? |
|---|---|---|---|
| `control.sock` | The control socket: `aria toggle`, `quit`, `update-ready` talk to the running service through it. One service at a time. | No (reaching it controls the dock) | Not while Aria runs; a stale one is replaced at start |
| `clients.sock` | The socket terminal clients connect to, `aria` in a terminal locally, `aria client-stdio` for `aria connect`. Mode `600`. | Reaching it is a terminal at the keyboard | Not while Aria runs |
| `jobs-<session>.sock` | One per session: how the session's Pi starts and reads background work. Mode `600`. Not made when the runtime folder fell back to `/tmp`. | Reaching it is control of that session | Not while Aria runs |
| `watch-<session>.sock` | One per session: the live view of the subagents. Mode `600`. | Same | Not while Aria runs |
| `j-<16 hex>.sock`, `w-<16 hex>.sock` | The same two sockets under a short name, used when the usual path would pass 100 bytes. | Same | Not while Aria runs |
| `face` | One word for what Aria is doing (`idle`, `thinking`, `reading`, `editing`, `working`, `delegating`, `asking`, `scheduled`, `done`, `error`, `sleeping`). The Omarchy bar widget reads it. | No | Yes: rewritten on the next change |
| `aria-secrets-<id>/` | Next to the runtime folder, not in it: the live copies of `auth.json` and `mcp-auth.json` while the service runs (`700`, files `600`). `<id>` is a short hash of the data folder, so each home has its own. The files go when the service quits (they stay if sealing a last change failed); the folder stays. | Yes | Not while Aria runs: Aria writes it back from the keyring |

The live folder is `$XDG_RUNTIME_DIR/aria-secrets-<id>` on Linux (the system's temporary folder when the variable is
unset) and `aria-secrets-<id>` in the per-user temporary folder on macOS (`/var/folders/…/T`, outside `~/.aria` and outside
backups). The sandbox hides `$XDG_RUNTIME_DIR` from the commands it runs, so a command the model starts cannot see any of
this ([safety](../guide/safety.md)).

## Binaries and services

| Path | What | Secret? | Safe to delete? |
|---|---|---|---|
| `~/.local/bin/aria` | The binary (`ARIA_BIN_DIR` moves it). A hub's `aria connect` runs `~/.local/bin/aria` on the server. | No | Only by uninstalling ([below](#what-the-installer-touches)) |
| `~/.config/systemd/user/aria.service` | Omarchy: starts the dock with the graphical session, restarts it on failure. | No | Only by uninstalling |
| `~/.config/systemd/user/aria-serve.service` | Hub: runs `aria serve`, starts with the user manager, restarts after 5 seconds on failure; its `PATH` begins with `~/.aria/node/bin` and `~/.aria/bin`. | No | Only by uninstalling |
| `~/Library/LaunchAgents/com.aria.dock.plist` | macOS: starts the dock at login in the desktop session, restarts it after a crash, sends its output to `~/.aria/logs/aria.log`. | No | Only by uninstalling |
| `~/.config/omarchy/plugins/aria.face/` | Omarchy: the face widget (`manifest.json` and `Face.qml`, which the binary carries). `aria bar install` puts it in the bar; `aria bar remove` takes it out. | No | Use `aria bar remove` |
| `~/.config/omarchy/shell.json.bak.<epoch>` | Omarchy: a copy of the bar's `shell.json`, made before the widget was placed. | No | Yes |
| `~/.agent-browser/browsers/` | The Chrome that `agent-browser` downloads. It lives outside `~/.aria`. | No | Yes: the browser check stops working until it is installed again |

The unit directory is `${XDG_CONFIG_HOME:-~/.config}/systemd/user`, and Omarchy's is `${XDG_CONFIG_HOME:-~/.config}/omarchy`.
Pinned versions are in the repository's `pi-version`, `node-version`, `engram-version`, `agent-browser-version` and
`pi-packages` files, not here.

## The keyring

With `credentials.keyring` on (the default), Aria keeps keys in the system keyring: the Secret Service on Linux, the login
keychain on macOS. Every value is stored as base64, and a value too long for one item is stored in pieces (`<account>#<n>`,
with the item itself reading `chunks:<n>`).

The service name is `aria` for the default data folder, and `aria:<data folder>` for any other, so a development or test
home never reads the real keys.

| Account | What |
|---|---|
| `key:<provider>` | An API key that was in `auth.json` (for example the OpenCode Go key). The file now holds a `!aria secret …` command in its place. |
| `file:auth.json`, `file:mcp-auth.json` | The two files Pi rewrites itself, sealed whole. The service seals a change within a second. |
| `file:<name>.prev` | A sealed copy kept aside when Aria could not merge it with a plain file that turned up. Rare. |
| `mcp:<server>:header:<name>`, `mcp:<server>:env:<name>` | A secret-looking value of `mcp.json`: every header of a remote server, and the `env` values whose name holds `KEY`, `TOKEN`, `SECRET`, `PASSWORD` or `AUTH`. |
| `user:<name>` | A secret you asked Aria to keep. `secrets.json` holds only its name. A command reads it as `ARIA_SECRET_<NAME>`; the model never sees the value. |

On Linux each item has the attributes `service` and `account`, and the label `Aria: <account>`. On macOS each item is a
generic password with service and account, labelled `<service>:<account>`. `aria keyring status` lists the accounts Aria
knows from its own files, by name (it never prints a value). `aria keyring off` writes the sealed files and every value
behind a command back into plain files (mode `600`) and deletes them from the keyring; it needs Aria stopped. `aria keyring
on` turns it on again and the service moves the keys at its next start. Secrets you keep (`user:<name>`) need the keyring:
without it nothing is saved. The design is in [the keyring spec](../superpowers/specs/2026-10-21-keyring-design.md); the
guide is [safety](../guide/safety.md).

## File modes

| Mode | What |
|---|---|
| `700` | `~/.aria`, `agent/`, `bin/`, `logs/`, `engram/`, the attachment folders, the runtime folder, the live credential folder, and `hub-src/` on a hub |
| `600` | `sessions.json`, `schedules.json`, `jobs.json`, `secrets.json`, `mcp.json`, `auth.json` and `mcp-auth.json` (plain or live), `agent/settings.json`, `agent/aria.json`, `agent/.aria-files`, attachment files, the sockets that Aria sets (`clients.sock` and the per-session ones), files a hub import writes and their `.bak` |
| `644` | `settings.json` as Aria saves it (it holds no secret); `/effort` and `/autocompact` in a session rewrite it as `600` |
| `755` | `~/.local/bin/aria`, the `pi` shim |

`control.sock` and `face` take the default mode; the `700` runtime folder is what keeps others out.

## What the installer touches

`install/install.sh` (also how you update; `--dry-run` prints without changing anything).

| It | On |
|---|---|
| installs the binary | `~/.local/bin/aria`: downloaded from the latest GitHub release of `i-montes/aria` (a chosen one with `ARIA_VERSION`) and checked against its `.sha256`, or the one you give with `--local`; on macOS it also signs it ad hoc as `com.aria.dock` |
| creates and fills | `~/.aria`: `bin/` (with `engram`), `pi/<version>/`, `agent/` (with the pinned packages), `agent-browser/<version>/` (not on a hub unless `--with-browser`), `node/` (a hub that needs it), `logs/` (macOS) |
| downloads a browser | `~/.agent-browser/browsers` (not on a hub unless `--with-browser`) |
| writes the service | `aria.service` (Omarchy), `aria-serve.service` (hub with `--headless`) or `com.aria.dock.plist` (macOS), and starts it |
| puts the face in the bar | Omarchy only, through `aria bar install`: the plugin folder, a `shell.json.bak.<epoch>` copy, then Omarchy's own `omarchy plugin enable aria.face` |
| installs system packages | Omarchy: `gtk3 webkit2gtk-4.1 gtk-layer-shell bubblewrap iproute2 libsecret alsa-lib vulkan-icd-loader` with `pacman` (asks for sudo). A hub: `bubblewrap iproute2` with `apt-get` or `pacman`, or prints the command. macOS: none |
| enables linger | A hub only: `loginctl enable-linger`, so the user manager runs with nobody logged in |

`install.sh --uninstall` stops and removes the service, removes the binary, and runs `aria bar remove` (Omarchy); on
Omarchy it also unbinds `SUPER + A` in the running Hyprland session. On a hub run it with `--headless`: without it the
installer looks for `aria.service`, removes the binary and leaves `aria-serve.service` enabled. Then it asks `Delete ~/.aria (your settings and
credentials)? [y/N]` and removes the folder only on `y`, and only if it looks like Aria's data. It does not remove:

- the keyring items. Run `aria keyring off` first if you want the keys written back into plain files and the keyring
  emptied of them, then delete the folder. Secrets you kept (`user:<name>`) stay in the keyring either way: delete them from
  the settings screen before you uninstall, or with your keyring's own tool (service `aria`).
- `~/.agent-browser`, the `shell.json.bak.<epoch>` copies, the system packages, and linger on a hub.
- On a hub, the `restrict,command="…/aria client-stdio"` line that `aria hub init --client-key` added to
  `~/.ssh/authorized_keys`. Remove it by hand.

`aria hub init` writes on the server, over ssh and after you say yes: `~/.aria/hub-src` (uploaded with `umask 077`), what
the installer does with `--headless`, the bundle of your settings and credentials into `~/.aria` (see `.bak` above), and,
with `--client-key`, one `restrict,command="…/aria client-stdio"` line in `~/.ssh/authorized_keys` (the sandbox on the hub
is checked first). The computer you run it from keeps nothing. See [the hub guide](../guide/hub.md).

## What Aria never touches

- `~/.config/hypr/`. The dock registers its shortcut with Hyprland while it runs, through Hyprland's own IPC, every time it
  starts; the installer never edits the folder. A scheduled task cannot be granted write access there either, nor to
  `~/.ssh`, `~/.gnupg`, `~/.aws`, the keyrings, the autostart and systemd folders, or `~/.pi`.
- `sshd_config`, the firewall and Tailscale, on a hub or anywhere. `aria hub init` only reads the ssh setup and warns you
  when the port is open to the internet.
- The `.git` of your projects. Checkpoints use a repository of their own in `~/.aria/checkpoints/`. A background subagent
  that works in a copy puts it in `<projects folder>/.aria-worktrees/`, inside the projects folder.
